# 行程通知系统 P0/P1 实施路线图（后端优先）

> 目标：在“仅后端建设、前端对接现有小程序”的约束下，把当前 MVP 演进到可上线、可观测、可持续优化的高可用系统。

## 1. 北极星目标与评分框架（10 分制）

- **业务结果（4 分）**
  - 投诉率下降（目标：上线后 1 个月相对基线下降 20%+）。
  - 好评率提升（目标：满意度 4-5 分占比提升 15%+）。
  - 漏发率下降（目标：关键通知漏发率 < 0.5%）。
  - 人效提升（目标：单管家日均干预次数下降 30%+）。
- **系统能力（4 分）**
  - 发送成功率（短信 + 企微兜底）≥ 99.5%。
  - 关键链路可观测（日志、指标、追踪）覆盖率 100%。
  - 规则配置化（无需改代码改阈值/模板）覆盖 P0 全场景。
  - 审计可追溯（谁、何时、向谁、发了什么）100%。
- **工程质量（2 分）**
  - 自动化测试覆盖核心路径（触发、编排、兜底、投诉升级、满意度跟进）。
  - 灰度与回滚流程可执行，RTO < 30 分钟。

## 2. 目标架构（与你当前仓库一一对应）

## 2.1 领域分层

- `integration`：对接易途 API、天气 API、短信网关、企业微信机器人/群管理。
- `trigger`：时间必发 + 条件触发（天气、情绪、投诉、行程变更）。
- `notification`：模板解析、发送编排、重试、人工介入、渠道兜底。
- `complaint`：情绪识别与投诉升级，触发管理员提醒。
- `survey`：行后满意度回收与低分自动跟进。
- `audit`：关键操作审计与合规留痕。

## 2.2 关键技术组件

- **数据库**：PostgreSQL（事务、审计、模板版本）。
- **消息队列**：Redis + Celery（异步发送、重试、延迟任务）。
- **调度器**：Celery Beat（早/中/晚固定时点 + 团级覆盖）。
- **缓存**：Redis（幂等键、短期上下文、限流计数）。
- **可观测**：Prometheus + Grafana + Sentry。
- **配置中心**：环境变量 + DB 配置表（后续可接 Apollo/Nacos）。

## 3. P0（必须）实施清单

## 3.1 目标与范围

- 行前：参团成功、出发提醒、风险提醒。
- 行中：每日早/中/晚提醒、天气/高风险场景触发、投诉升级。
- 行后：欢送词、满意度回收、低分跟进。
- **不在本期**：新游客端、小程序重构、复杂 BI 大屏。

## 3.2 渠道与发送主体

- 主渠道：短信（关键通知统一走短信）。
- 兜底渠道：企业微信（自动建群 + 管理员/管家通知）。
- 发送主体：系统自动为主，失败后人工介入（管家/管理员）。
- 失败策略：
  1. 短信失败自动重试 2 次（指数退避）。
  2. 仍失败则企微告警群发消息。
  3. 5 分钟未处理升级到管理员。

## 3.3 触发规则

- **必发节点**：
  - 行前 T-1 天提醒。
  - 行中每日早/中/晚固定时点。
  - 行后满意度邀请。
  - 投诉/情绪不稳定告警。
- **条件触发（天气）**：
  - 雨天、极寒、强紫外线、边境/高原等标签命中时触发对应模板。
- **审核策略**：固定模板免审核；自由编辑模板需管理员审核。

## 3.4 权限与审计

- 权限基线：除管家外，业务操作默认无权；模板和群发/重发/撤回仅管理员。
- 审计记录：所有发送、重发、撤回、模板变更、群创建/解散必须落库。

## 3.5 数据对接与一致性

- 易途 API：团、游客、行程、航班、酒店、保险等主数据。
- 行程变更：
  - 写入版本号（`itinerary_version`）。
  - 自动触发“变更通知”进群。
  - 客户确认后写回确认状态，防止并发覆盖。

## 3.6 P0 验收指标

- 发送成功率 ≥ 99.5%。
- 漏发率 < 0.5%。
- 模板渲染正确率 ≥ 90%。
- 观察期：上线后 1 个月。

## 4. P1（建议）实施清单

- 模板多版本管理（草稿/已发布/废弃）。
- 按季节/线路/人群自动选模板。
- A/B 文案测试（按团或用户随机分桶）。
- 报表导出与异常告警（按团、按线路、按管家）。

## 5. 分阶段落地计划（建议 8 周）

- **第 1-2 周：基础设施**
  - DB 表结构、消息队列、任务调度、统一日志与告警。
- **第 3-4 周：P0 主链路**
  - 触发引擎配置化、短信发送、企微兜底、审计日志。
- **第 5-6 周：投诉与满意度闭环**
  - 情绪识别阈值、投诉升级策略、低分自动跟进。
- **第 7 周：联调与压测**
  - 易途 API 联调、失败注入、峰值压测、容量评估。
- **第 8 周：灰度与上线**
  - 小流量灰度、观察指标、回滚演练、全量上线。

## 6. 最小数据模型（建议）

- `notification_task`：任务主表（团、客、模板、渠道、状态、重试、幂等键）。
- `notification_attempt`：每次发送尝试明细（请求、响应、错误码、耗时）。
- `trigger_rule`：规则配置（必发/条件、阈值、有效期、优先级）。
- `template` + `template_version`：模板与版本历史。
- `complaint_event`：投诉/情绪事件。
- `survey_response`：满意度结果与跟进状态。
- `audit_log`：关键操作审计。

## 7. 风险清单与控制

- **外部 API 不稳定**：设置超时、熔断、降级与本地重试队列。
- **误触发/重复发送**：全链路幂等键 + 去重窗口。
- **情绪识别误报**：阈值可调 + 人工确认回路。
- **群通知无人处理**：升级策略（5 分钟、15 分钟两级升级）。
- **模板错误导致批量事故**：发布前校验 + 灰度发布 + 一键回滚。

## 8. 你当前仓库下一步“立即可做”的 10 件事

1. 建立 PostgreSQL 模型与 Alembic 迁移。
2. 为 `notification` 增加真实网关适配器接口（短信/企微）。
3. 为 `dispatch` 增加重试与状态机。
4. 为 `trigger` 增加阈值表达式与优先级。
5. 为 `integration` 接入真实易途 API 与天气 API。
6. 落地 `audit_log` 持久化与查询接口。
7. 增加幂等中间层（按 `team_id + template + schedule_time`）。
8. 新增 UAT 场景测试集（行前/行中/行后 + 异常分支）。
9. 增加 Prometheus 指标：成功率、漏发率、重试率、人工介入率。
10. 建立上线 Runbook（告警、排障、回滚、值班）。

---

如果按以上执行，系统通常可以达到 **8.5~9.5/10**：
- P0 可保证“能跑、可控、可追责”；
- P1 可带来“持续优化与运营增长”；
- 关键在于 **配置化规则 + 渠道兜底 + 审计可观测 + 灰度回滚** 四件套。
